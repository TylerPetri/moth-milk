# Public-client and backend boundaries — Pass 2

The repository implements a SvelteKit server boundary, not the private commerce backend. Fixture passes demonstrate application behavior; they cannot establish backend authorization or real payment correctness.

| Area | Enforced here | Depends on private backend / remaining concern |
| --- | --- | --- |
| Public environment | Build/config and request guards permit four public names and validate formats. Public API URLs cannot contain credentials, path, query or fragment. Private `API_ORIGIN` is server-only. | A correctly formatted public value can still be sensitive if misused. Hosting runtime configuration and backend credentials were not inspected or changed. |
| Payment environment | Stripe client refuses a backend key that switches configured test/live mode. Stub public URLs must be loopback, cannot use live keys; server rejects stub `/v1/orders` submissions to non-loopback upstreams. Demo explicitly overrides all payment/shop/origin settings to synthetic local values. | Browser checks are not payment authorization. Backend must select the right Stripe account/environment, reject invalid payment methods and enforce amounts/idempotency/webhook verification. Ordinary live mode remains an existing supported feature; production settings are unchanged. |
| Account cookies | Host-only HttpOnly access/refresh cookies; SameSite Strict; Secure over HTTPS; session markers replace usable tokens in auth JSON. Logout clears legacy/current auth paths; SSR validates customer context through backend. | Backend verifies JWT signatures, issuer/audience, role, revocation and shop ownership. Cookie attributes do not encrypt content or protect against same-origin XSS. Refresh coalescing is process-local, not a distributed lock. |
| Same-origin proxy | Explicit route/method allowlist, Origin equality for mutations, bounded JSON bodies, no browser authorization/cookie/forwarding-header passthrough, server-controlled shop header. Redirects disallowed; upstream timeouts bounded. | Backend must honor the shop scope and bind every resource lookup to it. Shop UUIDs/host mapping are routing context, not secrets or authorization. Deployment must supply trusted host routing; multi-shop authorization cannot be certified with one fixture. |
| Receipt capabilities | Status reads accept a read proof or original key; resume/cancel require the original key. HttpOnly receipt cookies bounded to 10/30 days; imported emailed proof is removed from URL and excluded from completed summaries. Fixture tests verify omitted auth headers for capability requests, not account bypass generally. | Backend must authenticate capabilities, bind them to shop/order/action and enforce lifetime/replay/ownership. Keys in unfinished local attempts remain JS-accessible and can be copied by XSS/extensions. Moving them without a recovery migration could strand payments, so this behavior is retained and disclosed. |
| Checkout restoration | Original idempotency key saved before reservation; lost responses retry the same attempt. Unknown outcomes preserve marker/bag and suppress another payment; replacement requires verified server closure. New contact fingerprints are SHA-256 digests; legacy raw fingerprints migrate without changing keys/payment state, with a compare-before-write guard against overwriting newer state. | Digests reduce plaintext exposure, not anonymization: contact combinations can be guessed. Storage failures may prevent migration; recovery data is preserved instead of silently erased. Browser state/amounts are untrusted. Backend must reserve stock/price/tax and authorize restarts. |
| Contact data | Drafts in session storage (24-hour read expiry); submitted contact data in tab storage and HttpOnly `mm_checkout` cookie (up to 30 days). Completed receipt summaries omit contact/capabilities but retain order IDs, items, totals and supplied shipment/carrier/tracking metadata; these are still device-held order data. | Cookie data is unsigned/unencrypted client-held JSON and must not authorize or price orders. Same-origin scripts can request recovery JSON. Backend/operator privacy and retention requirements remain outside the repo. |
| URLs and logs | Receipt fragments and auth/reset/verification query tokens are consumed then removed from address bar. Referrer-Policy `no-referrer`; sensitive responses private/no-store. No application logging of credentials added. | Query parameters may reach ingress/history before browser removal, and Stripe can return intent parameters. Keep access logs, error monitoring and analytics away from capability bodies/URLs or redact them; external retention is not verified. Prefer backend-issued fragment receipt links when supported. |
| CSP / headers | Self scripts plus Stripe; self fonts; restricted connect/frame sources; object/base/form/frame-ancestor controls; nosniff, DENY embedding, no-referrer, permissions restrictions and HTTPS HSTS. | `style-src` allows inline styles and images allow HTTPS; CSP reduces XSS risk but is not a sanitizer. Gateway CORS, TLS, cache/CDN rules, logging and rate limits require operator review. |
| Local rehearsal | `npm run demo` binds UI/upstream to loopback, uses synthetic shop/account/order state and visibly labels simulation. Controlled demo test blocks external browser traffic and places only a fixture order. Missing-backend tests build/run with empty configuration and require a safe 503 plus working visual room. | Fixture login is deliberately not real authentication and has no real credentials/database. Never expose the fixture server publicly or interpret its responses as security or payment integration. |

## Pass 2 regressions

Unit coverage checks payment mode matching, stub configuration restrictions, legacy fingerprint migration and credential preservation. Desktop/mobile browser checks inspect raw persistent storage for contact leakage, reject live-key responses during prepare/resume, retain recovery keys without Stripe confirmation, verify missing-backend failure, and complete a visibly simulated local order. Existing outage, cancellation, reload, cookie, receipt and duplicate-payment protections remain in the full suite.

Outstanding: decide whether to accept browser recovery capabilities and 30-day contact recovery retention; validate backend tenant/ownership/capability rules and distributed refresh behavior in disposable test resources; assess low-severity framework/toolchain advisories. No live backend, customer data or charge is used for this review.
